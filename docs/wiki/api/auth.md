# 認証

**Atlasのデバイス認証(ゲスト型)を引き継ぐ。** API の仕様(リクエスト・レスポンス・エラー)は [API: DeviceService](device-service.md) にある。

1. **デバイス登録**: クライアントが生成した `secret_key` を送り、サーバーが `device_id` と `player_id` を発行する。発行するのは ID だけで、プレイヤー(`players` の行と初期データ)はまだ作らない
2. **トークンの発行**: `device_id` と `secret_key` を送り、アクセストークンを受け取る。有効期限は1時間で、有効なトークンは1デバイスにつき1つ(発行し直すと古いものは無効になる)
3. **要認証のAPI**: メタデータ `authorization: Bearer <token>` を付けて呼ぶ。無い・存在しない・期限切れなら `UNAUTHENTICATED` が返る
4. **サインイン**: 「プレイヤー未作成」(例: `PLAYER_NOT_FOUND`)が返ったら、サインアップ(デバイス登録で発行した `player_id` で、プレイヤーと初期データを作る)へ進む。サインアップはデバイス登録とは別の機能・別のAPI

- **認証の要否は、サービスのカスタムオプション `skip_auth` で表す**。v1で `skip_auth` を付けるのは、基盤のデバイス登録・認証のサービスだけ
- BAN・アカウント停止は `FAILED_PRECONDITION` + `ACCOUNT_SUSPENDED` で返す(再認証しても解決しないので `UNAUTHENTICATED` にはしない)
- gRPCのメタデータのキーは小文字にする

## `player_id` をデバイス登録で発行する

- **なぜ**: サインアップの前や、サインインできないとき(メンテナンス・通信エラー・アカウント停止)にも、クライアントが問い合わせ用に `player_id` を表示できるようにするため。特にアカウント停止中は認証の時点で `ACCOUNT_SUSPENDED` になり、サインインに進めない
- **発行するのは ID だけ**: プレイヤー(`players` の行と初期データ)はサインアップで作る。途中でやめた人の分で増えるのは `devices` の1行だけで、ニックネームや利用規約の同意も作成の前に挟める
- **サインアップ済みかは、クライアントは覚えずに毎回サインインで判断する**。`player_id` を持っていても、プレイヤーが作られているとは限らない。サインインの `PLAYER_NOT_FOUND` を `handledCodes` で受け取り、サインアップへ進む([エラー処理](../client/error-handling.md))
- アカウントの引き継ぎは、新しい端末の `devices.player_id` を引き継ぎ元の `player_id` に書き換える形になる(新しい端末用に発行した `player_id` は、`players` の行が無いまま使われずに終わる)

## 保存したアカウント情報が使えなくなったとき

端末に保存した `device_id`・`secret_key` が、接続先のサーバーで使えなくなることがある。本番で起きるのは次の場面。

| 場面 | 種類 |
|---|---|
| アカウントの引き継ぎで、古い端末の認証を無効にした | サーバーが意図して無効にした |
| アカウントを削除した(ユーザーの申し出・法令への対応。別の端末やサポート経由で削除すると、消された端末に情報が残る) | サーバーが意図して無効にした |
| DB をバックアップから戻した(その時点より後に登録した端末の行が消える) | 行が無い |
| 使われていない `devices` の行を掃除した | 行が無い |
| 運用のミス・バグで消した | 行が無い |

- **サーバーが意図して無効にするときは、行を消さずに理由を残す**。トークンの発行で、`secret_key` が合っていれば理由ごとの業務エラー(例: 引き継ぎ済み・削除済み)を返し、クライアントは理由に合った文言を出す。理由を返すのは `secret_key` が合ったときだけにする(`device_id` が存在するかを外から調べられないように)
- **行が無い・`secret_key` が合わないときは、今のまま区別せずに `UNAUTHENTICATED` を返す**。クライアントは「アカウント情報が見つからない」として、新しく始める(保存したアカウント情報を消して登録し直す)か、引き継ぎ・サポートへ進むかを選ばせる。**自動では登録し直さない**(ユーザーが気づかないまま、元のデータと別のアカウントで始まってしまうため)
- `devices` の行を掃除するときは、サインアップまで進んだ端末(`players` の行がある `player_id`)の行は消さない。消してよいのは、サインアップの前に離脱した端末の行だけ
- 開発中に接続先を切り替えて起きるものは、クライアントが接続先ごとに保存先を分けて防ぐ([認証とアカウント情報](../client/auth-account.md))
