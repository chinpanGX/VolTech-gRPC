# サーバーの状態(メンテナンス・強制アップデート・日付変更)

パッケージの状態の判定のクレート `status`(`server/rust/status/`)が持つ。サーバー時刻とゲーム内の日付のレスポンスヘッダー([3.8](../api/metadata.md))も、ここで付ける。

## 設定

DBの外の1つのファイルに置き、サーバーが数秒おきに読み直す(再起動せずに切り替えられる)。

```toml
# server_status.toml
[maintenance]
enabled = false
end_at = "2026-10-01T15:00:00+09:00"   # ダイアログに出す終了予定(省略可)

[min_version]   # プラットフォームごとの最低バージョン(リリースのたびに増やす整数)
ios = 120
android = 120
windows = 120

[game_day]
reset_hour = 4            # ゲーム内の日付が変わる時刻
timezone = "Asia/Tokyo"
```

- 読み込みに失敗したら、直前の状態を使い続ける。起動時に一度も読めなかったら、起動しない
- 読み込み元は trait にする。AWSに載せるときは、AWSの設定サービス(SSM Parameter Store など)から読む実装に差し替える(サーバーが複数台になっても状態がそろう)
- DBに置かないのは、メンテナンス中はDBを止めることがあり、判定できなくなる(`MAINTENANCE` ではなく `INTERNAL` が返る)ため

## 判定

- **メンテナンス**: v1はオン/オフだけ。オンなら全員に `MAINTENANCE` を返し、`end_at` があれば `metadata` に入れる。時刻が来ても自動では終わらず、フラグをオフにして終える。通常メンテと緊急メンテの区別はしない(緊急のときは終了予定を空にする)
- **強制アップデート**: リクエストのプラットフォームとアプリのバージョン([3.8](../api/metadata.md))を、プラットフォームごとの最低バージョンと比べ、小さければ `UPDATE_REQUIRED` を返す。整数なので比べ間違いが起きない
- **日付変更**: リクエストのゲーム内の日付が今の日付と違えば `DATE_CHANGED` を返す。**日付のヘッダーが無ければ判定しない**ので、トークン発行とサインインは判定に引っかからない(APIごとの除外の指定は要らない)。クライアントが日付を偽っても、ログインボーナスなどの切り替えはサーバーの時刻で判定するので、不正にはつながらない

## 実装で決めたこと

- **Layer は2つ**。`ServerStatusLayer`(強制アップデート → メンテナンスの判定と、レスポンスヘッダーの付与)は全サービスの外側に、`DateChangeLayer` は認証が必要なサービスにだけ `AuthLayer` の内側に付ける([リクエストの処理の流れ](request-flow.md) の順)
- **プラットフォームかバージョンのヘッダーが無い・読めないときは、強制アップデートを判定しない**。日付と同じ扱いにした。grpcurl や Postman でヘッダーを付けずに呼べるようにするため。強制アップデートは古いアプリを止める仕組みで、不正を防ぐものではないので、外せても困らない。基盤のクライアントは必ず付ける
- プラットフォームの値は小文字の `ios`・`android`・`windows`・`editor` の4つ。知らない値は、無いのと同じ(判定しない)
- **Unity のエディタは、OS によらず `editor` を送り、サーバーは強制アップデートを判定しない**。開発中に、最低バージョンを上げたせいでエディタから呼べなくなるのを防ぐため。エディタからの通信をログで見分けられる。強制アップデートの動きは、偽のサーバー(`FakeRpcErrors`)か、ヘッダーを付けたテストで確かめる
- `MAINTENANCE` の `metadata` のキーは `end_at`。値は設定の時刻を **UTC の RFC 3339**(例: `2026-10-01T06:00:00Z`)に直したもの。設定ではタイムゾーン付きで書けるが、クライアントが解釈する形を1つにするため
- ゲーム内の日付は、`timezone` の壁時計の時刻から `reset_hour` 時間を引いた日付。ヘッダーの形は `YYYY-MM-DD`。リクエストの日付は文字列のまま比べる(形が違えば日付が違うのと同じで、`DATE_CHANGED` になる)
- 設定は5秒ごとに読み直す(`server` の `main.rs`)。設定ファイルの場所は環境変数 `SERVER_STATUS_PATH`(既定はアプリが決める。samples は `Server/app/config/server_status.toml`、sandbox は `sandbox/server/config/server_status.toml`。どちらもリポジトリのルートからのパス)
- 設定の読み込みでは、知らないキーや範囲外の値(`reset_hour` が 0〜23 でない、知らないタイムゾーンなど)をエラーにする。書き間違いを、黙って既定値で動かさずに気づけるようにするため。読み直しで失敗したときは、ログに出して直前の設定を使い続ける
- **リクエストを受けたときのゲーム内の日付は、`ServerStatusLayer` がリクエストの extensions に `voltech_grpc_status::GameDate` として入れる**。ハンドラーは日付で決まる処理(無料ガチャなど)にこれを使い、レスポンスヘッダー `x-game-date` と `DateChangeLayer` の判定も同じ日付を使う。日付が変わる時刻をまたいだリクエストでも、処理に使った日付とクライアントに返す日付がずれないようにするため
- 読み込み元の trait は `StatusSource`、ファイルから読む実装は `FileStatusSource`。テストでは時計(`Clock`)も差し替えられる

## 後から足すもの

v1は、サーバー1台でエンジニアが自分で運用する前提の最小構成にしている。

| 時期 | 足すもの | 理由 |
|---|---|---|
| 一般のユーザーに公開する前 | ソフトメンテ(IPの許可リストの人だけ通す) | メンテ明けに、本番環境で動作確認してから公開するため。IPだけならDBを使わずに判定できる |
| 一般のユーザーに公開する前 | 設定の置き場所をAWSの設定サービスにする | サーバーが複数台になっても状態をそろえるため |
| 運用が大きくなってから | `player_id` の許可リスト | 認証の後にもう一度判定する形になる |
| 運用が大きくなってから | 通常メンテと緊急メンテの出し分け | 予約コードを分ければ、文言が自動で分かれる |
| 運用が大きくなってから | 管理画面 | エンジニア以外が操作でき、変更の記録を残すため |

- IPの許可リストでは、ALBが付けた `X-Forwarded-For` の**末尾**の値を使う。ALBは既にある値の末尾に接続元のIPを足すので、先頭の値はクライアントが自由に書ける。信頼できる中継が他にもある場合は、「末尾から何番目か」を設定で持つ
- メンテナンスの判定の対象外にするAPIが必要になったら、`skip_auth` と同じくサービスのカスタムオプションで表す

## 採らなかった案

| 項目 | 採らなかった案 | 理由 |
|---|---|---|
| サーバーの状態 | メンテナンスなどの状態をDBに置く | メンテナンス中にDBを止めると判定できない |
| 強制アップデート | ヘッダーが無いリクエストを `UPDATE_REQUIRED` にする | 開発中に grpcurl などで呼びにくくなる。不正を防ぐ仕組みではないので、厳しくしても得るものが無い |
| エディタのプラットフォーム | 動いている OS(Windows のエディタなら `windows`)を送る | macOS のエディタは送る値が無く、OS によって動きが変わる。最低バージョンを上げるとエディタから呼べなくなる |
| エディタのプラットフォーム | ビルド先(`#if UNITY_IOS` など)を送る | エディタで各プラットフォームの強制アップデートを試せるが、最低バージョンを上げるとエディタから呼べなくなるのは同じ |
| メンテナンスの終了予定 | 設定に書いた文字列をそのまま返す | タイムゾーンの書き方が何通りもあり、クライアントの解釈がぶれる |
