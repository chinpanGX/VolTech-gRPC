# docs/wiki の更新ルール

この wiki は、gRPC 基盤 VolTech gRPC(Unity クライアント + Rust サーバー)の設計と、使い方(API の仕様・リファレンス・環境構築)の置き場所。人と LLM の両方が読み、更新する。LLM は、`index.md` から読み始め、必要なページだけを開く。

いちばんの読み手はアプリ開発者。アプリを作る人が「何からやるか」「API を足すとき何をするか」を `guide/` だけで辿れるようにし、基盤開発者だけが要る説明は `appendix/` に置く。

## 読む人とエリア

| エリア | 読む人 | 書くこと |
|---|---|---|
| `guide/` | 基盤を使ってアプリを作る人(アプリ開発者。いちばんの読み手) | 何を・どう使うか。作る順の手順(始め方 → つなぐ → API を足す)、役割分担、通信の調べ方、版の上げ方、リファレンス |
| `api/`・`client/`・`server/`・`repo/` | 両方 | 設計(なぜそうしたか)と、API の規約・仕様 |
| `appendix/` | 基盤そのもの(このリポジトリ)を直す人(基盤開発者) | どこに何があり、どう直すか。コードの地図、直すときの流れ、このリポジトリの環境構築とテスト |

- 理由は設計のページに書き、`guide/`・`appendix/` からはリンクする(同じことを2か所に書かない)
- リファレンスのページは「どの型・関数を何に使うか」と組み込み方を書く。各メンバーの細かい説明はコードのドキュメントコメント(`///`)が正なので、全部を書き写さない

## 何が正か

| もの | 正の置き場所 | 扱い |
|---|---|---|
| API の形(RPC、メッセージ、エラーコード、`idempotency_level`) | `.proto` とそのコメント | wiki に手で書き写さない。frontmatter の `proto:` で結ぶ。API の仕様のページ(`api/device-service.md` など)の RPC の説明とリクエスト・レスポンスの表は、`.proto` のコメントから生成する(下の「API の仕様のページ」) |
| 使い方(環境構築、コマンド、クレートの組み込み方) | この wiki | README には書かない(下の「README」) |
| 型・関数の細かい説明(引数・戻り値・例外) | コードのドキュメントコメント(`///`) | wiki には、どれを何に使うかと組み込み方だけを書く。名前・引数・既定値はコードから写し、推測で書かない |
| 方針、規約、理由 | この wiki | 手で書く。LLM は下書きしてよいが、人がレビューする |
| 決まっていないこと | [open-questions.md](open-questions.md) | 決まったら、ここから消して該当ページに反映する |

編集しない原本はソースコード(`.proto` を含む)。コードや proto と wiki の食い違いに気づいたら、コードや proto を正として wiki を直す。proto のほうが間違っているときは、直す前に人に確認する。

## ページの形

- 1ページ1テーマ。先頭に frontmatter を置く
  - `title`、`status`、`area`(必須)
  - `related`: 関連するページ(wiki ルートからの相対パス、拡張子なし)
  - `proto`: そのページが説明する `.proto`(リポジトリのルートからの相対パス)
  - `code`: そのページが説明するコード(リポジトリのルートからの相対パス。フォルダでもよい)。コードが変わったときに、直すべきページを探すのに使う(`make wiki-affected`)。リファレンスと、特定のコードの設計を書いたページには必ず書く
  - `updated`: 最後に内容を変えた日
- `status` の値
  - `confirmed`: 確定
  - `deferred`: 保留(決めるのを後回しにしている)
  - `current`: 当面の方針(あとで変わり得る)
  - `appendix`: 基盤の設計とは別の付録
  - `open` / `reference` / `index`: 未確定の一覧 / 参考資料 / 目次
- **`status` を上げる(例: `current` → `confirmed`)のは人が決める**。LLM は、自分の判断で `confirmed` にしない
- 他のページへの参照は、相対リンクにし、リンクの文字はページ名にする(`[冪等性](../api/idempotency.md)`)。節番号は使わない
- 検討して見送った案は書かない。いまの形と、そうした理由だけを書く

## コードや .proto を変えたとき

手順はスキル `/wiki-update`(`.claude/skills/wiki-update/SKILL.md`)にまとめてある。

1. 変えた `.proto`・コードを `proto:`・`code:` に持つページを探す(`make wiki-affected`。ブランチ全体なら `make wiki-affected BASE=main`)
2. そのページの内容が変更後も正しいか確かめ、ずれていれば直す。`updated` を更新する
3. 実装の中で新しく決めたことは、該当ページに「実装で決めたこと」として足す
4. 決まっていなかったこと([open-questions.md](open-questions.md))が決まったら、その行を消し、決めた内容を該当ページに書く
5. `.proto` のコメントや RPC を変えたら、`make wiki-gen` で API の仕様のページを生成し直す
6. `make wiki-lint`(リポジトリのルートで `python scripts/wiki_gen.py --check` と `python scripts/wiki_lint.py`)を実行して、生成し直し忘れ・リンク切れ・frontmatter の抜けが無いことを確かめる。`make test` にも入っている

## API の仕様のページ

- RPC の説明とリクエスト・レスポンスの表は、`.proto` から生成する。ページに目印を置き、`make wiki-gen`(リポジトリのルートで `python scripts/wiki_gen.py`)を実行すると、その間が置き換わる。RPC は、そのページの frontmatter の `proto:` のファイルから探す

  ```
  <!-- generated:rpc voltech.v1.DeviceService/Register -->
  <!-- /generated -->
  ```

- **目印の間は手で直さない**。説明を直すときは `.proto` のコメント(RPC・メッセージ・フィールドの直前の `//`)を直して、生成し直す。フィールドの説明には、値の形(長さ・文字・単位)まで書く
- `.proto` に書けないこと(エラーと条件、呼ぶときの注意、値の作り方)は、目印の外に手で書く
- 生成し直し忘れは `make wiki-lint` がエラーにする(`wiki_gen.py --check`)

## README

- README は、そのフォルダを開いた人への入口だけにする。内容は書かず、wiki の該当ページへのリンクを置く(GitHub はフォルダを開くと README を表示し、クレートを持ち出したときにも読む場所が分かる)
- 説明を足したくなったら、wiki のページに書き、README にはリンクだけを足す

## ページを足す・分けるとき

- 新しいページは、該当エリアの `index.md` と、ルートの [index.md](index.md) の一覧に足す(足し忘れは lint が警告する)
- 1ページが長くなりすぎたら、テーマで分ける。分けたら、元のページからリンクを残す
- ページ名(ファイル名)は英語のスラグにする。後から変えるとリンクが切れるので、変えるときは参照元も直す

## 書き方

- 日本語で書く。「何をするか」より先に「なぜそうするか」を書く(判断の理由が、この wiki の価値)
- 実装名(クレート、型、ファイル)は `コード書式` にする
- 数値や名前は、コードや proto にあるものと一致させる。確かめられないものは、書かずに [open-questions.md](open-questions.md) に足す

## ブログ記事にするとき

- 記事は読み物、wiki は事実の置き場。記事の下書きは wiki とは別の場所に置く
- 種になるのは、各ページの「なぜそうするか」。なぜその形を選んだかを軸にする
- 記事と wiki が食い違ったら、wiki を正として記事を直す
