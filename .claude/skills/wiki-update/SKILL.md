# wiki の更新

コードの変更に合わせて `docs/wiki` を直す。書き方の決まりは `docs/wiki/CLAUDE.md` が正なので、最初に読む。

## 引数

- なし: コミットしていない変更を見る
- `main` などのブランチ・コミット: そこから分かれた後のこのブランチの変更と、コミットしていない変更を見る(`BASE=` で渡す)
- ファイルのパス(1つ以上): そのファイルを直接見る(`FILES=` で渡す)。引数がブランチかファイルか迷ったら、`git rev-parse --verify <引数>` が通ればブランチ・コミット、ファイルとして実在すればファイルとして扱う

## 手順

1. **直すべきページを探す**。リポジトリのルートで実行する

   ```
   make wiki-affected                         # 引数なし
   make wiki-affected BASE=main               # ブランチ・コミット
   make wiki-affected FILES="server/rust/auth/src/layer.rs Makefile"   # ファイル
   ```

   ページの frontmatter の `code:` と `proto:`(どちらもリポジトリのルートからのパス)に、変わったファイルが入っているページが「直すかを確かめるページ」に挙がる。どれにも結びつかない変更は「ページの無い変更」に挙がる。移動・名前変更したファイルは、元のパスと新しいパスの両方で挙がる(元のパスで挙がったページは、場所の書き換えが要る)。git がエラーを返したら(存在しないブランチなど)、そのメッセージを読んで引数を直す。

2. **変更を読む**。`git diff`(と、新しいファイルは中身)で、何が変わったかを確かめる。公開している型・関数・引数・設定・コマンド・ファイルの場所・振る舞いが変わったかを見る。内部だけの変更(リファクタリング、テストだけ)なら、wiki は直さなくてよいことが多い

3. **挙がったページを直す**。ページを読み、変更後のコードと食い違うところだけを直す
   - 名前・引数・既定値・パスは、コードからそのまま写す。推測で書かない。確かめられないことは書かずに `open-questions.md` に足す
   - 利用者向け(`guide/`)は「何を・どう使うか」、基盤開発者向け(`dev/`)は「どこに何があり、どう直すか」、設計のページは「なぜそうしたか」を書く。理由を `guide/` に重ねて書かず、設計のページへリンクする
   - 実装の中で新しく決めたことは、設計のページの「実装で決めたこと」に足す。検討して見送った案は「採らなかった案」に足す
   - 内容を変えたページは、frontmatter の `updated` を今日にする

4. **ページの無い変更を片付ける**
   - 既存のページが説明すべきものなら、そのページの `code:` にパスを足し、本文も直す
   - 新しい機能・ツール・公開 API なら、ページを足す(該当エリアの `index.md` と、ルートの `index.md` の一覧にも足す)
   - 説明の対象にならないもの(アプリのサンプルの細部など)は、そのままでよい。理由を報告に書く

5. **`.proto` を変えたとき**は `make wiki-gen` で API の仕様のページを生成し直す(目印の間は手で直さない)

6. **確かめる**

   ```
   make wiki-lint
   ```

   エラーが 0 になるまで直す。`code:` のパスが無くなっていれば、ファイルが移動・削除されているので、ページを直す

7. **報告する**。直したページ・足したページと、その理由を短く挙げる。直さなかった変更があれば、その理由も挙げる

## 注意

- `status` を `confirmed` に上げるのは人が決める。自分の判断で上げない
- 原本 `docs/feature-grpc-foundation.md` は編集しない
- 日本語で書く。Python などで日本語を含む文字列を置き換えるときは UTF-8 で読み書きする(perl の `-CSD` だけでは、スクリプト中の日本語が化ける)
